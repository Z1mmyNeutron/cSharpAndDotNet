Introduction 

Every program is, at its core, a set of instructions for working with data — storing it, transforming it, and making decisions based on it. This reading covers how C# stores that data through variables and types, and how operators let you act on it. By the end, you'll understand the difference between value and reference types, how to read user input and format output, and how to safely convert data from one type to another — all of which the Expense Tracker will depend on from this point forward.

var and type inference 

Instead of writing the type explicitly, you can let the compiler figure it out from the value on the right-hand side using var.  

csharp
123

By convention, local variables and parameters in C# use camelCase — totalAmount, not TotalAmount or total_amount. The compiler doesn't enforce this, but every C# codebase you'll encounter follows it.  

This isn't a different kind of variable — count is still genuinely an int underneath. var is just shorthand the compiler resolves once, at compile time. It's most useful when the type is obvious from context or unwieldy to type out; for everything else, writing the explicit type often keeps code easier to read at a glance.

Console.ReadLine and Console.WriteLine 

These two methods are how your console app talks to the person using it. WriteLine sends text out; ReadLine waits for the user to type something and press Enter, then hands that input back as a string.

Note that ReadLine always returns a string, regardless of what the user typed — even if they type 25, you get back the text "25", not the number. That's why Parse shows up immediately after almost every ReadLine call you'll write in this course.

Introduction 

So far, every program you've written has run the same way every time, top to bottom, line by line. Control flow changes that — it gives your code the ability to make decisions and repeat work. This reading covers conditionals, pattern matching, the four kinds of loops C# offers, and the small mistakes that trip up almost everyone the first time they write a loop. By the end, the Expense Tracker will be able to react to what a user enters, not just print fixed text.

if, else if, else 

The most basic decision in any program is a branch: do one thing if a condition is true, another if it isn't.

csharp
1234567891011121314
double balance = 150.00; if (balance < 0){    Console.WriteLine("Account overdrawn");}else if (balance < 50){    Console.WriteLine("Balance running low");}else{    Console.WriteLine("Balance healthy");}

Each condition is checked in order, top to bottom, and the first one that evaluates to true is the branch that runs — the rest are skipped entirely. else is your catch-all, the branch that runs when nothing above it matched.  


switch statements and switch expressions 

When you're checking one variable against many possible exact values, a switch is cleaner than a long chain of else if statements. C# supports two forms: the traditional statement form, and a newer, more compact expression form.  

csharp
12345678910111213141516171819202122
// Traditional switch statementstring category = "Food";switch (category){    case "Food":        Console.WriteLine("Essential spending");        break;    case "Entertainment":        Console.WriteLine("Discretionary spending");        break;    default:        Console.WriteLine("Uncategorized");        break;} // Modern switch expression — same logic, returns a value directlystring spendingType = category switch{    "Food" => "Essential spending",    "Entertainment" => "Discretionary spending",    _ => "Uncategorized"};

The expression form skips break entirely and uses _ instead of default for the catch-all case. It reads more like a lookup table than a series of steps, and it's the style you'll see more often in modern C# code.

Pattern matching basics 

Pattern matching extends switch beyond exact value checks — it lets you match based on a value's type, its range, or its shape.

csharp
123456789101112131415
double amount = 250.00; string sizeLabel = amount switch{    < 0 => "Invalid",    < 50 => "Small expense",    < 500 => "Medium expense",    _ => "Large expense"}; object input = 42;if (input is int number){    Console.WriteLine($"It's an integer: {number}");}

The second example, is int number, does two things in one step: it checks whether input is actually an int, and if so, hands you that value already cast into a new variable called number. This is the foundation pattern matching builds on, and it shows up again when working with custom types in Module 2.

break and continue 

Both keywords change a loop's normal path, but in opposite ways. break exits the loop immediately, skipping everything left in it. continue skips just the current iteration and moves straight to the next one.  

csharp
123456789101112131415
foreach (int amount in new[] { 10, -5, 20, 30 }){    if (amount < 0)    {        continue;   // skip this one, move to the next    }     if (amount > 25)    {        break;      // stop the loop entirely    }     Console.WriteLine($"Processing: {amount}");}// Output: Processing: 10  →  Processing: 20  (then stops at 30)

Common pitfalls: off-by-one, infinite loops 

Two mistakes account for the majority of loop bugs, and both are worth recognizing on sight rather than debugging from scratch each time.  


csharp
1234567891011121314
// Off-by-one — this throws an IndexOutOfRangeExceptionint[] amounts = { 10, 20, 30 };for (int i = 0; i <= amounts.Length; i++)   // should be < , not <={    Console.WriteLine(amounts[i]);} // Infinite loop — count never changes, condition never becomes falseint count = 0;while (count < 5){    Console.WriteLine("Looping forever...");    // missing: count++;}

The fix for both is the same habit: before running a loop, trace through the first and last iteration by hand and confirm the loop variable actually moves toward the condition that ends it.

Data: types, values, and conversion 

Lesson 1.2 introduced the two fundamentally different ways C# stores data. Value types — int, double, bool, char — copy the actual data when assigned to a new variable, so the two variables become fully independent. Reference types — string, arrays, and later, classes — copy a pointer to shared data instead, so two variables can end up pointing at the very same object. var doesn't change either of these behaviors; it just lets the compiler infer the type from the assigned value rather than you naming it explicitly.

Conversion between types came in four flavors, and the distinction between them matters in practice, not just in theory. Implicit conversion is automatic and safe — no data lost. Explicit conversion (a cast) accepts possible data loss, like a double losing its decimal part when cast to int. Convert and Parse both turn strings into numbers, but Parse throws immediately on invalid input while Convert handles null gracefully — a distinction that matters every time you process something typed in by a user, since Console.ReadLine always returns a string, regardless of what was actually typed.

Operators and control flow, working together

Lesson 1.3 then gave you the structures that use those operators to actually steer a program. if/else if/else and switch (in both its traditional and modern expression form) choose between paths based on a condition. ____________Introduction 

Up to this point, every program you've written has lived inside one block of code. That works for small programs, but it breaks down fast as logic grows — the same few lines get copy-pasted everywhere, and a single bug means hunting down every copy. Methods solve this by giving a piece of logic a name and a single home. This reading covers how to define and call methods, the different ways C# lets you pass data into them, how to write code that reads clearly to someone else, and how to use the debugger to see exactly what your code is doing when it doesn't behave as expected.

Defining and calling methods 

A method is a named, reusable block of code. You define it once, then call it by name as many times as you need, anywhere in your program.

csharp
123456789
// Defining a methodstatic double CalculateTotal(double price, int quantity){    return price * quantity;} // Calling itdouble total = CalculateTotal(4.50, 3);Console.WriteLine($"Total: ${total:F2}");   // Total: $13.50

The method's signature — its name, parameters, and return type — is the contract other code relies on. Anywhere in the program that needs this calculation now calls CalculateTotal instead of repeating the math, so a bug fix or a change in logic only has to happen in one place.  


Parameters: value, ref, out, optional, named 

Not all parameters behave the same way. By default, C# passes arguments by value — the method gets a copy. The other keywords change that behavior for specific situations.  

csharp
1234567891011121314151617181920212223242526
// Value (default) — the method gets a copy, original is untouchedvoid TryDiscount(double price){    price = price * 0.9;   // only changes the local copy} // ref — the method can modify the caller's actual variablevoid ApplyDiscount(ref double price){    price = price * 0.9;   // changes the original variable} // out — used when a method needs to return more than one valuebool TryParseAmount(string input, out double amount){    return double.TryParse(input, out amount);} // optional — has a default value if the caller doesn't supply onedouble CalculateTax(double amount, double rate = 0.08){    return amount * rate;} // named — the caller specifies which parameter each value belongs todouble tax = CalculateTax(amount: 100, rate: 0.05);

ref and out look similar but solve different problems: ref is for when a method needs to modify a value that already exists, out is for when a method needs to produce a brand-new value the caller doesn't have yet — TryParse is the most common example you'll encounter, since it returns both a success flag and the parsed result at once.

Return types and void 

A method's return type tells you what kind of value comes back when it finishes. If a method doesn't need to hand anything back — it just performs an action — its return type is void.

csharp
1234567891011
// Returns a valuedouble GetTotal(double price, int quantity){    return price * quantity;} // Returns nothing — just performs an actionvoid PrintReceipt(string item, double price){    Console.WriteLine($"{item}: ${price:F2}");}

Every path through a method with a non-void return type must return a value of that type — the compiler enforces this, so a missing return on some branch is caught before the program ever runs.

Method overloading 

Overloading lets multiple methods share the same name as long as their parameter lists are different. The compiler picks the right one based on what you pass in.

12345678910111213
double CalculateTotal(double price, int quantity){    return price * quantity;} double CalculateTotal(double price, int quantity, double discount){    return price * quantity * (1 - discount);} // The compiler chooses based on how many arguments you passCalculateTotal(4.50, 3);          // calls the first versionCalculateTotal(4.50, 3, 0.1);     // calls the second version

This is useful when a few versions of the same idea make sense — calculating a total with or without a discount — rather than inventing a separate, less obvious name for each variation.

Scope and variable lifetime 

A variable only exists within the block of code where it's declared — its scope. Once that block ends, the variable is gone.


csharp
123456789101112
void ProcessExpense(double amount){    double tax = amount * 0.08;   // scoped to the whole method     if (amount > 100)    {        double surcharge = 5.00;   // only exists inside this if block        tax += surcharge;    }    // surcharge is no longer accessible here — it's out of scope    Console.WriteLine($"Tax: ${tax:F2}");}

A variable declared inside a loop is recreated fresh on every pass and disappears at the end of each one — this is exactly why a loop counter declared inside for (int i = 0; ...) can't be read outside the loop.

Naming conventions and clean code basics 

Code is read far more often than it's written, and consistent naming is the cheapest way to make that reading easier. C# convention uses PascalCase for method names and class names, and camelCase for variables and parameters.

csharp
1234567891011
// Clear, conventional namingdouble CalculateMonthlyTotal(double dailyAverage, int daysInMonth){    return dailyAverage * daysInMonth;} // Unclear — works, but costs the next reader timedouble Calc(double d, int n){    return d * n;}

A good method name describes what it does well enough that you rarely need to read its body to understand its purpose. A method that does one clear thing is also easier to test, debug, and reuse than one that does several unrelated things at once — that single-responsibility habit will matter more once methods start calling each other inside the Expense Tracker.

Debugging: breakpoints, step controls, watch window, call stack 

When a program doesn't behave the way you expect, reading the code alone often isn't enough — the debugger lets you pause execution and inspect exactly what's happening, line by line.


In VS Code, setting a breakpoint is as simple as clicking in the margin to the left of a line number — a red dot appears, and running with Debug instead of Run will pause there automatically. From that paused state, the Watch window lets you type in any variable to see its current value, and the Call Stack panel shows exactly how the program got to that line, which is often the fastest way to find where a wrong value first appeared.
