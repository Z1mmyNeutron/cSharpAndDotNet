Why testing matters 

A test is code that checks other code. Without tests, you find out something broke when you happen to run the program and notice — or worse, when a user does. With tests, you find out the moment the bug is introduced, before it ever ships.


This matters most as a program grows. A change to CalculateTotal in Lesson 2.1 might look safe in isolation, but if ten other methods depend on it, manual checking can't realistically cover every case — a test suite can, every time, automatically.

xUnit: [Fact], [Theory], Assert, Arrange-Act-Assert 

xUnit is the testing framework you'll use to write and run tests for the Expense Tracker. A [Fact] is a test that always checks the same single case. A [Theory] is a test that runs multiple times with different input data, supplied through [InlineData].

Arrange-Act-Assert is the structure nearly every test follows, in that order: set up what the test needs, run the one thing being tested, then check the outcome. Assert.Equal is the most common check, but xUnit also provides Assert.True, Assert.NotNull, Assert.Throws, and others for different kinds of expectations.  


A test for the Expense Tracker might check that a negative amount throws NegativeAmountException, or that GroupBy correctly totals expenses by category — anything you'd otherwise verify by hand, written once and run automatically forever after.

Git: repository, commit, branch, remote 

Git tracks every change made to a project over time, letting you go back to any earlier point, and work on new features without risking what already works.

 A commit isn't automatic — Git only saves what you explicitly add and commit, which is intentional. It lets you group related changes into one meaningful snapshot, rather than recording every keystroke as its own entry in the project's history.  


GitHub: push, pull, clone 

GitHub hosts a copy of your Git repository online, which is what makes a project shareable, backed up off your machine, and collaborative.

clone is how you get a copy of a project that already exists on GitHub onto your own machine. push sends your local commits up to GitHub once you're ready to share them; pull brings down any commits made elsewhere — by you on another machine, or by a teammate — that you don't have locally yet. For the capstone, pushing your finished Expense Tracker to GitHub is what makes it an actual portfolio piece, visible and reviewable by anyone with the link.
